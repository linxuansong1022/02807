# Music4All-Onion 推荐系统项目方案

**项目名称：融合行为相似性与音频聚类的多样化音乐推荐**

**英文名称：Personalized and Diverse Music Recommendation with Behavioral Similarity and Audio Clustering**

- 适用课程：02807 Computational Tools for Data Science
- 适用团队：4–5 人
- 数据版本：Music4All-Onion v2
- 方案日期：2026 年 10 月 27 日
- 当前状态：项目设计阶段，尚未下载全量数据或运行实验
- 参数说明：以下规模、阈值和参数均为建议起点，第一周完成小样本试验后锁定

## 1. 项目目标与范围

主任务是在系统已经认识的歌曲目录中，为用户推荐 **20 首他尚未听过、但可能感兴趣的歌曲**。

这里的“新歌发现”是指：歌曲对系统已知，但对当前用户尚未听过。推荐目标是未来一段时间内用户实际听到的这些歌曲。

项目结合：

1. **课程主题一：相似项查找——MinHash / LSH**
2. **课程主题二：一般聚类——k-means**
3. **课外新方法：MMR 多样性重排**

项目主要研究准确率、检索效率和推荐多样性之间的关系。成果是一个可复现的离线推荐流程及其对照实验。

## 2. 研究问题

| 编号 | 研究问题 | 对应实验 | 希望检验什么 |
|---|---|---|---|
| RQ1 | LSH 能否降低相似用户检索成本？ | 精确 Jaccard 搜索与 MinHash / LSH 比较 | 在较高近邻召回率下，比较次数、查询时间和内存是否下降 |
| RQ2 | 音频聚类能否改善个性化推荐？ | 行为推荐与“行为＋音频簇偏好”比较 | 歌曲内容是否提供了听歌行为之外的有效信息 |
| RQ3 | MMR 能否改善多样性，同时控制准确率损失？ | 加入和移除 MMR 的对照 | 在保持推荐相关性的同时，是否覆盖更多音乐类型和歌曲 |

对于 RQ3，预先设置一个验证集选型标准：

> NDCG@20 的相对下降不超过 5%，同时尽量提高推荐多样性。

该标准是项目自行制定的取舍条件，不是数据集官方要求，也不是实验结果承诺。最终仍需在测试集上如实报告准确率和多样性的变化。

## 3. 整体方法与两个课程主题的结合

### 3.1 方法流程

~~~mermaid
flowchart TD
    A["推荐时可见的听歌历史"] --> B["MinHash / LSH 检索相似用户"]
    B --> C["候选歌曲与行为推荐分数"]
    D["歌曲音频向量"] --> E["标准化与 k-means 聚类"]
    E --> F["用户对音频簇的偏好"]
    A --> F
    C --> G["融合相关性评分"]
    F --> G
    G --> H["MMR 多样性重排"]
    D --> H
    H --> I["推荐 20 首用户未听过的歌曲"]
~~~

### 3.2 课程主题一：MinHash / LSH 相似用户召回

将用户表示为他在推荐时点之前听过的歌曲集合：

$$
H_u = \{i \mid \text{用户 }u\text{ 在推荐时点之前听过歌曲 }i\}
$$

用 Jaccard 相似度衡量两个用户的共同听歌偏好：

$$
J(H_u,H_v)
=
\frac{|H_u \cap H_v|}{|H_u \cup H_v|}
$$

实现步骤：

1. 根据用户听歌集合生成 MinHash 签名。
2. 对签名进行 LSH 分带和分桶，找到候选相似用户。
3. 只对候选用户计算精确 Jaccard 相似度。
4. 选取约 50 名最相似的用户。
5. 根据邻居听过的歌曲及其相似度，为当前用户生成候选和行为推荐分数。
6. 排除当前用户已经听过的歌曲。

行为推荐分数可以使用相似邻居的加权投票。LSH 负责减少需要进行精确比较的用户数量；它是否真正更快，需要通过实验判断。

### 3.3 课程主题二：音频 k-means 聚类

使用提供的音频向量，对歌曲进行标准化和聚类。

对于每名用户，统计其历史歌曲在各个音频簇中的分布，形成用户对不同歌曲群的偏好。例如，用户历史中较大比例的歌曲属于某个簇，则该簇中的候选歌曲获得额外相关性分数。

注意：音频簇表示“声音特征相近的歌曲群”，不能未经验证就将其等同于真实音乐流派。

### 3.4 融合行为分数与音频簇偏好

采用简单、可解释的融合方式：

$$
\operatorname{rel}(u,i)
=
(1-\alpha)\,\widetilde{s}_{CF}(u,i)
+
\alpha\,\widetilde{p}(u,c_i)
$$

其中：

- $s_{CF}(u,i)$：相似用户给歌曲 $i$ 的加权推荐分数。
- $c_i$：歌曲 $i$ 所属的音频簇。
- $p(u,c_i)$：用户对该音频簇的历史偏好。
- 波浪号：表示将两个分数分别归一化后再融合。
- $\alpha$：聚类信息的权重，由验证集选择。

聚类结果会直接影响推荐排序，因此它是解决方案的组成部分，而不只是可视化或附加分析。

## 4. 课外新方法：MMR 多样性重排

MMR（Maximal Marginal Relevance）通过逐首选择歌曲，兼顾相关性与列表内的非重复性。

每一步选择：

$$
i^*
=
\arg\max_{i \in C \setminus S}
\left[
\lambda\,\operatorname{rel}(u,i)
-
(1-\lambda)
\max_{j \in S}
\operatorname{sim}_{audio}(i,j)
\right]
$$

其中：

- $C$：候选歌曲集合。
- $S$：已经选入推荐列表的歌曲。
- $\operatorname{rel}(u,i)$：融合后的个性化相关性分数。
- $\operatorname{sim}_{audio}(i,j)$：映射到 $[0,1]$ 的音频向量余弦相似度。
- $\lambda$：相关性与多样性的权衡参数。
- 第一次选择时，重复惩罚设为零。

当 $\lambda=1$ 时，完全按照相关性排序；较小的值更强调与已有歌曲的差异。

本项目将经典 MMR 方法应用于音乐推荐，并研究参数取舍，不将 MMR 算法本身作为原创贡献。

参考：[MMR 原始论文](https://www.cs.cmu.edu/afs/cs/Web/People/jgc/publication/MMR_DiversityBased_Reranking_SIGIR_1998.pdf)

## 5. 数据与预处理

### 5.1 数据版本与文件

固定使用 [Music4All-Onion v2](https://zenodo.org/records/15394646)。

主方案使用三个文件；下表为压缩文件大小。

| 文件 | 用途 | 压缩大小 |
|---|---|---:|
| `userid_trackid_timestamp.tsv.bz2` | 构建历史、时间切分和未来听歌目标 | 约 2.2 GB |
| `id_ivec256.tsv.bz2` | 音频聚类及 MMR 音频相似度 | 约 85.8 MB |
| `id_genres_tf-idf.tsv.bz2` | 独立的流派多样性评价 | 约 3 MB |

主流程从时间戳文件生成当时可见的历史和计数。进行时间评估时，不能直接将覆盖整个时期的播放次数表用作训练输入。

歌曲内容特征的覆盖范围和听歌记录的覆盖范围不同，需根据歌曲 ID 对齐后再确定实验目录。

### 5.2 用户抽样与清洗

建议处理顺序：

1. 固定随机种子，抽取约 5,000 名用户。
2. 保留这些用户在选定数据范围内的完整听歌历史。
3. 分块读取播放日志，检查字段、时间戳、完全重复记录和缺失值。
4. 检查歌曲 ID 与音频、流派特征的对齐情况。
5. 使用稀疏用户—歌曲矩阵，避免构建全量稠密矩阵。
6. 将“是否听过”作为初始行为信号，重复播放次数可留作后续扩展。

### 5.3 全局时间划分

在全局时间轴上选择两个切点，初始目标约为：

| 数据段 | 事件比例目标 | 用途 |
|---|---:|---|
| 训练集 | 70% | 建立目录、画像、相似用户索引与初始模型 |
| 验证集 | 15% | 选择参数及准确率—多样性取舍 |
| 测试集 | 15% | 最终评估 |

需记录对应的真实日期，并保持时间先后关系。比例是起点，不替代对实际用户活跃度和数据分布的检查。

仅依据训练期确定歌曲目录，例如：

- 歌曲至少被 5 名训练用户听过。
- 歌曲有有效的音频和流派向量。
- 用户至少拥有 20 首符合目录条件的训练历史歌曲。

标准化器、音频聚类、用户画像、热门度和 LSH 索引都只能使用相应推荐时点之前可见的信息。

参考：[推荐系统离线评估中的时间泄漏研究](https://arxiv.org/abs/2010.11060)

### 5.4 验证与最终测试

验证阶段使用训练期构建的模型和历史进行参数选择。

参数确定后：

1. 保持已经确定的歌曲目录与参数。
2. 合并训练和验证行为，重建用户画像、热门度和 LSH 索引。
3. 评估测试期的推荐结果。
4. 过滤用户在训练和验证两段中已经听过的歌曲。

测试目标是用户在测试期实际听过、此前未听过、且属于固定目录的歌曲。

没有符合条件的新歌目标的用户，无法计算本任务的 Recall；需报告相应人数和排除比例。

### 5.5 必须报告的数据统计

- 过滤前后的用户数、歌曲数和事件数。
- 训练、验证、测试的真实时间范围。
- 用户历史长度的分布。
- 音频与流派特征的有效覆盖率。
- 固定歌曲目录覆盖了多少测试新歌。
- 最终可参与推荐评价的用户数量。

这些统计用于说明研究结论适用于哪些用户和歌曲。

## 6. 候选生成与对照实验

### 6.1 固定候选集合

先将候选集合设为 500 首：

1. 根据相似邻居的行为推荐分数选取候选。
2. 排除用户已听过的歌曲。
3. 候选不足时，使用训练期热门歌曲补齐。
4. 记录热门填充比例，帮助判断 LSH 候选是否充足。

比较聚类和 MMR 时，必须使用同一套候选歌曲。

### 6.2 五组主实验

| 方法 | 行为召回 | 聚类偏好评分 | MMR |
|---|---|---|---|
| M0：热门推荐 | 全局热门 | — | — |
| M1：行为推荐 | LSH 相似用户 | — | — |
| M2：加入音频聚类 | 同 M1 | 是 | — |
| M3：加入 MMR | 同 M1 | — | 是 |
| M4：完整方案 | 同 M1 | 是 | 是 |

实验解释：

- M0 与 M1：判断个性化行为推荐相对热门推荐的表现。
- M1 与 M2：判断音频聚类偏好评分是否有效。
- M1 与 M3：判断 MMR 单独带来的影响。
- M2 与 M4：判断在聚类方案中加入 MMR 的影响。
- M3 与 M4：判断在 MMR 方案中加入聚类评分的影响。

M1—M4 共享完全相同的 500 首候选；M0 是独立的简单基准。

### 6.3 LSH 检索效率实验

在固定的一批约 200 名查询用户上，比较：

- 精确 Jaccard 相似用户搜索。
- MinHash / LSH 候选检索，再进行精确 Jaccard 重排。

记录：

1. 精确 Top-50 邻居被找回的比例。
2. 实际进行精确比较的用户数量。
3. 索引构建时间。
4. 查询时间。
5. 峰值内存。

可逐步增加索引中的用户规模，观察效率变化。

LSH 在小数据上未必更快。如果维持高召回率需要大量候选，或索引开销超过节省的计算，应如实报告并解释。

## 7. 实验评价

### 7.1 指标

| 指标 | 回答的问题 |
|---|---|
| Recall@20 | 用户后来实际听的新歌中，有多少被推荐出来 |
| NDCG@20 | 相关歌曲是否排在推荐列表前部 |
| 候选召回率 | 真实目标有多少在进入重排之前已经被漏掉 |
| 流派多样性 | 推荐歌曲在独立流派表示上是否具有更大差异 |
| 目录覆盖率 | 所有用户的推荐合起来覆盖了多少首目录歌曲 |
| 运行时间与内存 | 推荐流程的计算成本是否可接受 |

流派多样性可以采用推荐歌曲之间的平均流派向量余弦距离。

**流派特征仅用于评价，不参与音频聚类和模型打分。** 这样可以减少使用模型自身优化目标证明多样性的循环。

### 7.2 端到端评价原则

- Recall / NDCG 的目标集合必须包含目录中全部符合条件的测试新歌。
- 没有进入候选集的真实目标仍应计入漏召回。
- 不仅在 500 首候选中重新挑选正负例进行最终评价。
- 所有方法使用同一批合格测试用户、歌曲目录和过滤规则。
- 对所有方法采用一致的推荐列表长度与补齐规则。

抽样评价可能改变模型之间的比较结论，因此需要区分候选阶段指标和最终推荐指标。

参考：[On Sampled Metrics for Item Recommendation](https://research.google/pubs/on-sampled-metrics-for-item-recommendation/)

### 7.3 随机性与不确定性

- 固定用户抽样和数据划分。
- 运行约 3 个算法随机种子。
- 报告算法随机性造成的指标波动。
- 对同一批用户的指标差异进行成对 bootstrap，计算置信区间。

离线结果支持的是行为预测与排序结论，不能直接等同于真实用户满意度的提升。

## 8. 参数与搜索策略

| 参数 | 起始设置或小范围搜索 |
|---|---|
| MinHash 签名长度 | 64、128 |
| LSH 分带 | 从每带 1、2 行开始，依据验证集近邻召回和比较量调整 |
| 相似邻居数 | 先固定 50 |
| 候选歌曲数 | 先固定 500 |
| 音频簇数 | 20、50、100 |
| 聚类融合权重 $\alpha$ | 0、0.2、0.5 |
| MMR 权重 $\lambda$ | 1、0.9、0.7、0.5 |
| 最终推荐数 | 20 |

分阶段选择参数：

1. 先确定可用的 LSH 配置。
2. 再选择音频簇数与融合权重。
3. 最后研究 MMR 的准确率—多样性曲线。
4. 参数在验证集选择完毕后冻结，再进行最终测试。

不要直接照搬课件中的 LSH 分带参数，需先检查本数据中用户听歌集合的相似度分布。
